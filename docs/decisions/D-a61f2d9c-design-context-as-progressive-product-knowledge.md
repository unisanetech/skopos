# Decision: Design Context As Progressive Product Knowledge

## Decision

Add **Design Context** as a bounded, versioned, progressively disclosed knowledge
capability within the existing Skill system.

Design Context is not a new Skill, Product Interface Design module, package, runtime
authority, or inspiration feed. Product Interface Design remains Structure, Behavior,
and Finish. It is the first consumer of a Design Context Library containing Domain
Guides, Experience Guides, Design Signals, and Source Notes.

One generated Context Brief selects the smallest relevant subset for a Task. Project
truth, existing components and tokens, and platform requirements outrank the Library.
All selected content consumes the existing Task-wide Skill budget.

## Context

Product Interface Design improves several recurring coding-agent failures, but recent
showcases also demonstrated that a capable agent can repeatedly fall back to familiar
visual conventions. The requested correction was initially described as adding current
trends and links to admired products.

That description identifies useful research inputs but not the durable capability.
Embedding links or visual fashions directly in core guidance would:

1. age the Skill quickly
2. encourage recognizable imitation
3. expand every Task's context
4. make live network state part of ordinary execution
5. confuse popularity with product fit
6. blur Product Interface Design with future public-page ownership

The durable requirement is contextual judgment grounded in accepted project truth and
reviewed external evidence.

## Accepted Rules

1. Use `Design Context` as the capability name and `Design Context Library` as the
   maintained collection.
2. Use `Domain Guide`, `Experience Guide`, `Design Signal`, `Source Note`, and
   `Context Brief` as the canonical artifact vocabulary.
3. Keep Structure, Behavior, and Finish as the complete Product Interface Design
   capability model.
4. Resolve Design Context only after compatible Skill selection.
5. Prefer project and platform authority over every library record.
6. Load a bounded task-specific subset and charge it to the existing Skill budget.
7. Treat links as provenance for concise original observations, not as runtime
   instructions or templates.
8. Exclude expired and retired records from new selections.
9. Record both maturity and recommendation for time-sensitive Design Signals.
10. Require an originality statement for every external principle projected into a
    Context Brief.
11. Keep routine selection local and deterministic; use browsing only for researched
    maintenance.
12. Give the Library an inspectable version and digest while retaining one exact
    accepted combined Skill identity.
13. Require deterministic selection proof, blinded behavioral comparison, independent
    human review, and real-project proof before promotion.
14. Keep public-page narrative and conversion guidance outside Product Interface
    Design.

## Rejected Alternatives

### Add a trend guide to Finish

Rejected because it would turn time-sensitive observations into permanent core
guidance, load irrelevant content, and imply that visual fashion is finish quality.

### Maintain a list of top product links

Rejected because an unqualified link list has no applicability, freshness, failure
mode, originality, or authority contract.

### Browse popular products during every design Task

Rejected because ordinary execution would become nondeterministic, expensive, slow,
and difficult to reproduce. It would also expose the agent to changing promotional
surfaces without reviewed interpretation.

### Create a separate trend or inspiration Skill

Rejected because the capability has no independent user outcome. It supports another
Skill's judgment and would otherwise duplicate selection, context, evaluation, and
acceptance authority.

### Freeze a small set of admired brands as templates

Rejected because it would encode trade dress, narrow creative range, and make the
result depend on who is currently fashionable.

### Rely on the model's general design knowledge

Rejected as the sole solution because model knowledge is undated, weakly attributable,
and cannot be accepted, expired, or evaluated as an exact project source.

## Consequences

1. Product Interface Design stays compact and conceptually stable.
2. Time-sensitive knowledge can evolve without renaming the Skill or adding modules.
3. Library maintenance becomes an explicit reviewed responsibility.
4. Exact acceptance and evaluation must include Library identity.
5. An expired Library may reduce Design Context to durable guides or core Skill
   guidance rather than silently using stale signals.
6. The first implementation needs schema, selector, budget, provenance, explanation,
   and expiry fixtures before any visual evaluation.
7. The current Product Interface Design efficacy result remains unchanged and
   inconclusive. A Library-backed identity requires fresh proof.
8. Future public-page or domain-specific Skills may consume the same Library through
   separately owned guides without copying its sources.
